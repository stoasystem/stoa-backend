## Question

采用哪一个仓库作为测试执行与结果索引入口，如何固定四仓库候选、衔接当前 main push 部署和正式 gate，并按哪些里程碑完成实施验收？遇到现有部署路径与新增门禁冲突时，先接入报告还是立即阻断部署？

建议复用 backend 的候选与跨仓库布局，前端维护浏览器用例，infra 维护资源检查，docs 维护最终流程；CI 执行固定测试，Codex 分析结果。分批次先建立可信基线与真人答疑闭环。决议应明确实施顺序、文件归属、旧验证策略的兼容和每批完成标准，不创建第二套发布框架。

待用户讨论的组织方案：以 backend 作为本地测试记录入口；backend、frontend、infra 分别执行各自既有适用测试，docs 作为需求与验收依据。固定四仓库提交及未提交差异，记录实际测试输入；真实测试另核对实际部署版本。结果按运行编号保存在 backend 的 .scratch/stoa-codex-testing/runs/，保留命令、环境、结果、脱敏证据与问题复现。顺序为版本/环境/费用与测试集合预检、既有本地适用检查、独立环境中的核心流程基线、汇总报告；受既定总时限及停止规则约束。需要代码或配置变更才能运行的项目记为阻塞，不进行接入改造。文档仅整理已批准决议和运行步骤，不改 CI 或部署流程。
