### Already delivered and reusable

  teacher onboarding, token validation, central resource authorization, and a
  219-route backend authorization inventory.
- Phase 473: owner-bound upload/chunk/promotion/OCR flow, supported file

  callback-origin validation, result convergence, allowance/reminder views,

  explicit manual-waiver boundary.

### Confirmed remaining Web gaps

- Login-code request and confirmation intentionally return `deferred`; the Web
  has no login-code, recovery, refresh, or server logout adapter.
- Web registration still offers `tutor`, sends fields rejected by the backend,
  and maps unknown roles to `student`.
- No generated or automatically checked OpenAPI-to-Web adapter boundary exists.
- Web upload still targets a multipart `/files` contract that the backend does
  not expose; the implemented backend uses intents, chunks, and completion.
- Practice preview/result/mistake/hint shapes disagree, including a
  pre-submission Web `correctAnswer` field and missing idempotency.
- Teacher Web adapters call `/tutors`; the canonical backend prefix is
  `/teachers`.
- Dashboard, lesson-result, question-bank, classroom, upload, assistant/booking,
  and several admin routes retain static, in-memory, or placeholder truth.
- The manual Web route metadata is not executable or complete: active and
  metadata routes drift.
- Existing browser tests are primarily demo-backed, route-intercepted, or
  MockWebSocket tests. They prove UI states, not integrated product journeys.

### Confirmed remaining infrastructure and operations gaps

- Existing CDK stacks are useful but do not yet prove environment import/drift,
  complete retained-route runtime resources, or deployed WebSocket lifecycle.
- Phase 473's real S3 multipart/version/promotion/restart and deployed cleanup
  scheduler/log observations, plus Phase 475's live DynamoDB and provider-effect
  observations, remain exact external obligations rather than local passes.
- No `$connect`, `$disconnect`, subscribe/refresh route handlers, authorizer, or
  WebSocket API deployment exists.
- Direct realtime events currently combine a user channel with a role channel;
  intersection-based matching can deliver a user-specific event to unrelated
  same-role connections.
- WebSocket fanout reads at most the first 500 connections and can stop after the
  first unknown/retry/cancel outcome.
- The Web places access token, user ID, and role in the WebSocket URL and has no
  real-server WebSocket test.
- Backend private telemetry is strong, but retained backend exception stacks and
  generic Web log fields can still leak content or provider details.
- `/health` is liveness-only; dependency readiness, global correlation, critical
  business alarms, and staged synthetic probes are incomplete.
- Practice, WebSocket, teacher, admin, and notification paths still contain
  first-page or hard-limit reads without an exhaustive retained-route inventory.

safe WebSocket channel authorization, deployed lifecycle handlers,
indexed/paginated fanout and stale cleanup, client
reconnect/order/dedupe/polling, and one real browser notification. Missing
external authority is exact `NOT RUN` and `HOLD`.

### Phase 480 — Operational Evidence, Pagination And Synthetic Probes

it never implements a second release or rollback mechanism. Phase 475's older
deployment/production-smoke assignment is superseded: deployment/rollback stays
in Phase 474, and production smoke remains separately authorized or exact

### Phase 481 — Evidence Reconciliation And Early-Test Decision

valid same-candidate receipt already exists, does not implement feature fixes,
